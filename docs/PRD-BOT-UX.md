# AI Coding Agent Bot 交互体验重设计 PRD

> 文档状态：最终版
>
> 版本：V1.0
>
> 日期：2026-10-18
>
> 适用端：飞书优先，Telegram 同步兼容
>
> 产品范围：手机端远程管理 Codex 工作区、会话与任务

## 1. 产品摘要

本次改版要把 Bot 从“依赖命令和会话编码的远程终端”变成“可直接看懂、点选、回复的会话工作台”。

用户不需要记命令、不需要输入会话 ID，也不需要猜普通消息会发到哪里。任何时候，用户都能明确看到：

1. 当前在哪个工作区；
2. 当前默认发送到哪个会话；
3. 该会话正在运行、等待回复、排队还是已完成；
4. 下一条消息会产生什么结果；
5. 如何一键切换会话、新建会话、切换工作区或停止任务。

核心交互原则是：**先明确目标，再发送内容；能点选就不要求输入；回复哪条消息，就回到哪段会话。**

## 2. 背景与问题

现有产品已经支持多会话、工作区切换、会话接管、任务排队和交互按钮，但整体仍围绕“焦点会话”“会话前 8 位”和命令组织，用户要先理解系统内部模型才能正确操作。

### 2.1 当前主要问题

- 会话以编码为主要识别方式，用户难以分辨每个会话在做什么。
- “继续会话”“新建会话”“切换工作区”入口分散，缺少稳定的首页。
- 普通消息默认发往焦点会话，但焦点不够显眼，容易误投。
- 后台会话状态变化可能干扰用户对“当前目标”的理解。
- 回复 Bot 消息时，消息的原会话信息没有用于路由。
- `/sessions`、`/project`、`/new` 等命令对熟练用户有效，但对手机端日常使用不友好。
- 多会话同时输出时，只有短编码提示来源，缺少会话名称和工作区上下文。
- 运行、等待用户、排队、完成等状态没有形成统一、易扫读的视觉语言。
- 停止、切换、接管等高影响操作缺少一致的确认和结果反馈。

### 2.2 用户原话对应的产品要求

| 用户诉求 | 产品要求 |
|---|---|
| “我想继续哪个会话？” | 用会话名称、工作区、摘要、状态和最近时间展示；提供“继续”按钮 |
| “我想新建会话？” | 首页固定提供“新建会话”，先选工作区，再输入任务 |
| “我想换工作区？” | 首页固定提供“切换工作区”，使用按钮列表而不是路径输入 |
| “说话时可以指定哪个会话” | 支持回复 Bot 消息自动定位原会话，也支持发送前通过按钮选择目标 |
| “不要输入一长串会话编码” | ID 仅用于诊断详情，不作为正常操作入口 |
| “给一些按钮选项” | 所有高频动作均提供可点击按钮，并在点击后给出明确反馈 |

## 3. 目标与非目标

### 3.1 产品目标

- 新用户在不阅读帮助文档的情况下，30 秒内完成首次任务。
- 用户最多 2 次点击即可进入任一最近会话并继续对话。
- 用户发送普通消息前，能明确知道目标工作区和目标会话。
- 会话选择、工作区切换、新建会话均可通过按钮完成。
- 回复历史 Bot 消息时，系统自动、可靠地路由到该消息所属会话。
- 多会话并行时，每条关键消息都有清晰来源，并且后台活动不改变用户手动选择的目标。
- 高风险或不可逆操作有确认；普通继续对话保持轻量。

### 3.2 非目标

- 本版本不替代 Codex 本身的任务规划或代码执行能力。
- 不在聊天窗口中实现完整 IDE、文件树或代码评审器。
- 不允许通过 Bot 继续旧 Claude 会话；旧 Claude 会话仍为只读监控。
- 不要求用户管理底层进程、rollout 文件或完整会话 ID。
- 本 PRD 不定义桌面 Web 看板的全面重构，只规定其与聊天端共享的状态语义。

## 4. 用户与核心场景

### 4.1 目标用户

主要用户是已经在电脑上使用 Codex、希望通过手机远程下达任务和跟进结果的开发者。用户通常同时维护多个代码仓库，也可能有多个并行会话。

### 4.2 核心场景

1. 打开 Bot，查看当前工作区和最近会话。
2. 继续昨天的某个任务。
3. 在指定工作区新建一个独立会话。
4. 回复某条历史结果，让原会话继续修改。
5. 在多会话并行时处理某个会话的提问或审批。
6. 切换工作区并选择该工作区最近使用的会话。
7. 查看运行进度、排队任务和错误原因。
8. 停止一个指定会话，而不影响其他会话。
9. 接管本机已有的空闲 Codex 会话。

## 5. 产品信息架构

产品采用三层结构：

```text
工作区 Workspace
└── 会话 Session
    └── 消息 / 任务 Turn
```

- **工作区**：代码仓库或项目目录，是任务执行边界。
- **会话**：同一上下文内的连续对话，必须属于一个工作区。
- **消息/任务**：用户发给某个会话的一次请求。

用户界面不得用“全局焦点”解释这套关系。对用户统一使用“当前会话”或“发送目标”。内部可以保留 `current_session_id`，但后台事件不得自动改变用户手动选择的当前会话。

## 6. 全局交互原则

### 6.1 目标始终可见

涉及输入任务的卡片必须显示：

```text
📁 工作区：ai-coding-agent-bot
💬 当前会话：优化会话管理
🟢 状态：可继续
```

用户切换后，Bot 必须立即回复“已切换”，不能静默改变状态。

### 6.2 按钮优先，命令兜底

- 首页、会话、工作区、等待回复、停止任务均提供按钮。
- 命令继续保留，作为熟练用户和兼容入口。
- 正常流程不展示或要求输入会话 ID。
- 会话 ID 只出现在“更多详情”和诊断信息中，可复制但不突出。

### 6.3 用户选择稳定

- 用户手动选中的当前会话保持不变，直到用户再次切换、新建或明确退出。
- 其他会话完成、报错、等待回复或输出消息，不得抢占当前会话。
- 新建会话成功后，新会话成为当前会话。
- 接管会话成功后，被接管会话成为当前会话。

### 6.4 回复即路由

用户回复某条 Bot 消息时，系统读取该消息绑定的 `workspace_id` 与 `session_id`，将回复投递到原会话。回复路由优先于当前会话。

若原会话可继续，直接发送，并反馈目标名称；若原会话不可继续，展示原因和替代操作，不得静默发给其他会话。

### 6.5 先防误投，再追求少一步

当系统无法唯一确定目标时，不执行任务，而是展示会话选择卡：

```text
要把这条消息发到哪里？
[💬 优化会话管理 · 当前]
[💬 修复登录问题]
[➕ 新建会话]
[取消]
```

## 7. 导航与首页

### 7.1 触发方式

- 用户发送 `/start`、`/menu` 或点击任一“返回首页”按钮。
- 用户长时间未交互后再次发送模糊消息，系统可先显示轻量目标提示，不强制回首页。

### 7.2 首页卡片

```text
🤖 Coding Agent

📁 当前工作区：ai-coding-agent-bot
💬 当前会话：优化会话管理
🟢 可继续 · 2 分钟前更新

最近进展：已完成现状分析，准备撰写 PRD

[继续当前会话]  [选择会话]
[新建会话]      [切换工作区]
[查看运行任务]  [任务队列]
[帮助与设置]
```

### 7.3 首页行为

| 按钮 | 行为 |
|---|---|
| 继续当前会话 | 展示当前会话详情和输入提示，不发送空任务 |
| 选择会话 | 打开当前工作区的会话列表，支持查看全部工作区 |
| 新建会话 | 进入工作区选择；默认工作区排第一 |
| 切换工作区 | 打开工作区选择卡 |
| 查看运行任务 | 只显示运行、等待用户和排队中的会话 |
| 任务队列 | 展示队列及逐项取消入口 |
| 帮助与设置 | 展示常用动作、命令兜底和通知设置 |

首页没有当前会话时，“继续当前会话”替换为主按钮“开始第一个任务”。

## 8. 会话列表与会话卡片

### 8.1 默认排序和分组

会话列表按以下顺序展示：

1. 需要用户处理；
2. 正在运行；
3. 当前会话；
4. 最近更新的空闲或已完成会话。

默认仅展示当前工作区最近 8 个会话，提供“查看其他工作区”和“查看更多”。

### 8.2 会话命名

- 首次创建时，使用首条任务生成 8–20 个汉字的可读标题。
- 禁止把会话 ID 作为主标题。
- 标题重复时，在副标题中用工作区和更新时间区分。
- 用户可通过“更多 → 重命名”修改标题。

### 8.3 会话卡片规范

```text
🟡 优化会话管理
ai-coding-agent-bot · 等待你的回复
刚刚更新
问题：PRD 是否只覆盖飞书端？

[回复] [设为当前]
[查看详情] [停止]
```

状态为已完成时：

```text
⚪ 修复登录问题
doctor-wang · 已完成
昨天 21:40 更新
结果：修复 token 刷新并通过测试

[继续] [查看详情] [更多]
```

### 8.4 会话卡按钮规则

| 状态 | 主按钮 | 次按钮 |
|---|---|---|
| 等待用户 | 回复 | 设为当前、查看详情、停止 |
| 运行中 | 查看进度 | 设为当前、追加任务、停止 |
| 排队中 | 查看队列 | 设为当前、取消排队 |
| 空闲/已完成 | 继续 | 设为当前、查看详情、更多 |
| 错误 | 查看错误 | 重试、继续、更多 |
| 外部 Codex 空闲 | 接管并继续 | 查看详情 |
| 外部 Codex 运行中 | 查看状态 | 不提供接管，说明需先在原终端停止 |
| Claude 会话 | 查看详情 | 标记“只读”，不展示继续或接管 |

“设为当前”成功后，原按钮更新为“✓ 当前会话”，并发送简短确认。

## 9. 新建会话流程

### 9.1 标准流程

```text
首页 → 新建会话 → 选择工作区 → 输入任务 → 创建并执行
```

工作区选择卡：

```text
➕ 新建会话
请选择任务所在的工作区：

[⭐ ai-coding-agent-bot · 当前]
[doctor-wang]
[agentops-j]
[选择其他工作区]
[取消]
```

选择后：

```text
已准备新会话
📁 工作区：ai-coding-agent-bot

请直接发送第一条任务。发送前不会创建空会话。

[更换工作区] [取消新建]
```

### 9.2 新建态规则

- “下一条消息新建”必须是显式、可见的临时状态。
- 该状态显示目标工作区，并在 10 分钟无输入后过期。
- 用户点击取消或切换到现有会话后，立即清除新建态。
- 新建态不得仅依赖一个不可见布尔值。
- 第一条任务发送成功后创建会话，并自动设为当前会话。
- 发送失败时保留草稿和新建态，提供“重试”与“取消”。

## 10. 继续会话与消息发送

### 10.1 普通消息路由优先级

系统按以下优先级确定目标，命中后停止：

1. 用户回复的 Bot 消息绑定的会话；
2. 用户刚刚从卡片选择的待回复会话；
3. 可见的新建会话临时状态；
4. 用户手动设定的当前会话；
5. 当前工作区唯一可继续的会话；
6. 无法唯一确定时，弹出目标选择卡。

历史兼容的 `@会话前缀` 仍可使用，但不在主界面宣传。

### 10.2 发送前提示

当前会话明确且最近 30 分钟内由用户选中时，直接发送，避免每次确认。

以下情况发送前需要选择或确认：

- 当前会话为空；
- 当前会话已被删除或不可访问；
- 当前工作区与会话工作区不一致；
- 当前目标来自旧的自动恢复状态，用户本次尚未确认；
- 消息可能触发新会话但用户未选择工作区。

### 10.3 发送后回执

发送成功后立即展示轻量回执：

```text
✓ 已发送到「优化会话管理」
📁 ai-coding-agent-bot · 🟢 执行中
[查看进度] [停止]
```

任务进入队列时：

```text
🕓 已加入「优化会话管理」队列 · 前面还有 1 个任务
[查看队列] [取消这条]
```

## 11. 回复 Bot 消息定位会话

### 11.1 消息绑定

Bot 发出的以下消息都必须持久化绑定关系：

- Codex 正文输出；
- 阶段进度和完成通知；
- 等待用户回复的问题；
- 审批或候选项卡片；
- 错误、重试和停止通知；
- 会话详情中的可回复消息。

绑定数据至少包含：

```text
channel
chat_id
bot_message_id
workspace_path
session_id
message_type
created_at
```

### 11.2 回复行为

- 用户回复某条 Bot 消息时，系统优先投递到该消息所属会话。
- 投递后不强制改变当前会话；若用户选择“同时设为当前”，才更新当前会话。
- 为减少困惑，回执明确显示“已回复到「会话名称」”。
- 回复等待问题后，原等待卡更新为“✓ 已回复：内容摘要”，按钮失效。
- 重复点击或重复事件必须幂等，不得发送两次。

### 11.3 绑定失效处理

如果消息绑定找不到或会话已不可继续：

```text
这条消息对应的会话已无法继续。
你可以：
[查看原会话] [在同一工作区新建会话]
[选择其他会话] [取消]
```

系统不得回退到当前会话并静默发送。

## 12. 工作区切换

### 12.1 工作区卡片

```text
📁 选择工作区

⭐ ai-coding-agent-bot
当前 · 3 个会话 · 1 个运行中
[切换到这里] [查看会话]

doctor-wang
2 个会话 · 最近昨天使用
[切换到这里] [查看会话]

[➕ 添加工作区] [取消]
```

### 12.2 切换后的行为

- 仅切换工作区，不自动新建会话。
- 若该工作区有最近的可继续会话，展示建议但不自动选中：

```text
✓ 已切换到工作区「doctor-wang」
最近会话：修复登录问题 · 昨天更新
[继续最近会话] [选择其他会话] [新建会话]
```

- 若该工作区无会话，主按钮为“新建会话”。
- 工作区路径只在详情中完整展示，主界面使用短名称。

## 13. 运行中、等待与多会话并行

### 13.1 统一状态

| 状态 | 图标 | 用户含义 |
|---|---|---|
| 新建待输入 | ✍️ | 已选工作区，等待第一条任务 |
| 排队中 | 🕓 | 已收到，等待执行资源 |
| 运行中 | 🟢 | Codex 正在处理 |
| 等待用户 | 🟡 | 需要回复或选择 |
| 已完成/空闲 | ⚪ | 可以继续对话 |
| 已停止 | ⏹️ | 本轮已终止，可继续新任务 |
| 错误 | 🔴 | 本轮失败，需要处理 |
| 只读 | 🔒 | 只能查看，不能由 Bot 继续 |

### 13.2 多会话输出

非当前会话的消息必须带可读来源：

```text
🟢「修复登录问题」有新进展
📁 doctor-wang

已定位到 token 刷新逻辑……

[打开会话] [设为当前] [停止]
```

当前会话的连续流式输出可使用紧凑样式，但每组输出首条仍需包含会话名称。

### 13.3 等待用户处理中心

多个会话同时等待时，Bot 发送聚合提醒，不连续刷屏：

```text
你有 2 个会话需要处理
[优化会话管理 · 选择方案]
[修复登录问题 · 确认权限]
[稍后提醒]
```

点击后打开对应问题卡。处理一个后自动返回剩余待处理列表。

### 13.4 后台状态规则

- 后台事件只更新所属会话状态。
- 后台事件不得改变当前工作区、当前会话或新建态。
- 会话完成后保留为可继续状态，不自动归档。
- 通知去重以 `session_id + turn_id + event_type` 为键。

## 14. 提问、选择与审批

### 14.1 普通提问

```text
🟡「优化会话管理」需要你的回复
📁 ai-coding-agent-bot

PRD 是否只覆盖飞书端？

[仅飞书] [飞书 + Telegram]
[输入其他回复] [稍后处理]
```

- 点击选项后，按钮变为已选择状态并禁用。
- “输入其他回复”进入绑定该会话的一次性回复态。
- 用户也可以直接回复该卡片。

### 14.2 高风险审批

审批卡必须包含动作、影响范围、目标会话和工作区：

```text
⚠️「部署生产环境」请求确认
📁 service-api

动作：执行 git push
影响：将当前分支推送到 origin

[确认执行] [拒绝]
[查看详情]
```

- 默认按钮不得预选“确认”。
- 确认和拒绝均需要结果回执。
- 超时后标记“已超时”，不得继续接受旧按钮。

## 15. 会话详情

详情页展示：

```text
💬 优化会话管理
🟢 运行中

工作区：ai-coding-agent-bot
当前任务：生成最终 PRD 并提交推送
开始时间：15:15
最近更新：刚刚

最近进展：正在整理完整交互与验收标准
```

## 16. 停止、取消与错误恢复

### 16.1 停止指定任务

- 从某个会话卡点击“停止”，只停止该会话当前运行或等待项。
- 若会话有排队任务，确认卡必须说明排队任务是否保留。

```text
停止「优化会话管理」当前任务？
该会话还有 1 条排队任务，默认保留。

[停止当前任务] [停止并清空该会话队列]
[取消]
```

### 16.2 停止全部

“停止全部”不放在首页主操作区，只在运行任务页的更多菜单中提供，并要求二次确认，明确显示受影响数量。

### 16.3 错误卡

错误信息使用“发生了什么—是否已产生影响—下一步”结构：

```text
🔴「优化会话管理」本轮执行失败
原因：Codex CLI 连接超时
影响：任务未完成，已保留会话上下文

[重试本轮] [继续输入]
[查看技术详情] [返回首页]
```

技术栈、退出码和完整异常仅放在“技术详情”。

## 17. 通知与防打扰

- 运行开始只发送一次回执。
- 心跳默认合并到可更新的进度卡，避免不断产生新消息。
- 同一会话的连续工具进度在 30 秒窗口内合并。
- 等待用户、完成、失败为高优先级通知。
- 非当前会话完成时保留来源卡，不改变当前目标。
- 提供“仅通知需要我操作”和“通知全部进展”两个级别。
- 夜间静默仅抑制普通进度，不抑制用户主动打开会话后的结果。

## 19. 文案规范

### 19.1 术语

| 内部术语 | 用户界面用词 |
|---|---|
| focus / 焦点 | 当前会话 / 设为当前 |
| cwd / project path | 工作区 |
| session ID | 会话编号，仅诊断详情出现 |
| managed session | 可控制会话 |
| pending interaction | 等待你的回复 |
| adopt | 接管并继续 |
| resume | 继续会话 |

### 19.2 文案原则

- 按钮用“动词 + 对象”，如“选择会话”“停止任务”。
- 成功反馈以“✓ 已……”开头；失败反馈说明下一步。
- 不向普通用户暴露布尔状态、进程名或内部键名。
- 不使用“焦点被抢占”“绑定 session”等工程表述。
- 会话名称始终使用中文引号标识，例如「优化会话管理」。

## 21. 数据与状态设计要求

### 21.1 会话展示模型

每个会话至少需要：

```text
session_id
display_title
workspace_path
workspace_label
status
last_summary
last_user_message
created_at
updated_at
is_controllable
is_current
source
```

### 21.2 用户选择状态

需分别持久化：

- `selected_workspace_path`：用户手动选择的工作区；
- `selected_session_id`：用户手动选择的当前会话；
- `selection_source`：按钮、命令、恢复或默认推断；
- `selected_at`：选择时间；
- `draft_new_session`：新建态目标工作区与过期时间。

运行事件不得写入 `selected_session_id`。

### 21.3 消息路由索引

消息绑定记录要支持按渠道消息 ID 快速查找，持久化跨重启恢复，并设置合理保留期。至少保留 90 天或与本地会话生命周期一致，以较短者为准。

### 21.4 幂等与并发

- 按钮回调使用唯一 action ID，并记录已处理状态。
- 同一消息回调重复到达时返回原处理结果。
- 每个会话内部任务保持顺序，不同会话可并行。
- 路由决策完成后，将目标会话随排队任务一起持久化，后续当前会话变化不得改变已排队任务目标。

## 23. 验收标准

### 23.1 首页与选择

- [ ] `/start` 后一屏内可看到当前工作区、当前会话、状态及六个核心入口。
- [ ] 没有当前会话时，不显示会误导用户的“继续当前会话”。
- [ ] 用户可完全通过按钮完成选择会话、新建会话和切换工作区。
- [ ] 正常流程不要求用户查看或输入会话 ID。

### 23.2 路由正确性

- [ ] 回复会话 A 的 Bot 消息时，即使当前会话是 B，消息仍只发送到 A。
- [ ] 回复路由成功后明确显示目标会话名称和工作区。
- [ ] 消息绑定失效时不自动发送到当前会话。
- [ ] 后台会话完成、等待或报错不会改变当前会话。
- [ ] 已排队消息的目标不会因用户随后切换会话而变化。
- [ ] 多次收到同一按钮回调时只执行一次。

### 23.3 新建会话

- [ ] 点击新建后必须先明确工作区，再等待第一条任务。
- [ ] 新建态在界面可见，可取消，会自动过期。
- [ ] 第一条消息发送成功前不创建空会话。
- [ ] 创建成功后新会话成为当前会话。
- [ ] 创建失败时保留用户输入并提供重试。

### 23.4 多会话

- [ ] 所有非当前会话通知均显示会话名称和工作区。
- [ ] 多个等待项以聚合入口展示，可逐个处理。
- [ ] 停止某个会话不会停止其他会话。
- [ ] 一个会话运行时，用户可以选择另一个会话并发送任务。

### 23.5 卡片状态

- [ ] 已点击、已超时或已处理的按钮不可再次触发动作。
- [ ] 卡片状态过期时提供刷新入口。
- [ ] 所有成功、失败、停止和排队操作都有回执。
- [ ] 飞书和 Telegram 的语义一致；若组件能力不同，降级为等价按钮和文本。

## 25. 实施优先级

### P0：解决误投与找不到入口

- 新首页和固定核心按钮；
- 可读会话名称与会话卡片；
- 工作区选择、新建会话显式状态；
- 当前会话稳定，不被后台事件改变；
- 回复 Bot 消息路由到原会话；
- 每次发送、排队、停止均有目标明确的回执；
- 按钮幂等和过期处理。

### P1：提升多会话效率

- 等待处理中心；
- 会话重命名；
- 队列逐项取消；
- 进度卡合并更新；
- 通知级别设置；
- 工作区会话分组与搜索。

### P2：体验增强

- 草稿和离线待发送；
- 会话归档；
- 更丰富的进度摘要；
- 跨端一致的 Web 看板深度链接。

## 26. 发布计划与回滚

### 26.1 分阶段发布

1. 先上线展示层：首页、会话名称、状态卡和按钮入口。
2. 再上线稳定选择状态与新建态，保留原命令兜底。
3. 上线消息绑定与回复路由，先记录影子路由结果，验证后启用实际投递。
4. 最后上线卡片更新、聚合通知和通知设置。

### 26.2 兼容与回滚

- 保留全部原命令至少两个版本周期。
- 新旧路由日志使用同一匿名 trace ID，便于比对。
- 回复路由异常时必须进入目标选择，不得回退到隐式当前会话。
- 可通过配置关闭新版卡片，但“后台不得抢当前会话”和“回复失效不得误投”属于安全规则，不应回滚。

## 27. 最终决策

V1 的产品中心不再是命令列表，而是“当前工作区 + 当前会话 + 明确动作”。会话 ID 从用户主流程中移除；所有高频操作按钮化；回复某条 Bot 消息成为最自然、最高优先级的会话指定方式。

产品是否好用，以用户能否在手机上快速回答三个问题为最终判断标准：

1. 我现在在哪个工作区？
2. 我下一句话会发到哪个会话？
3. 我怎样用一次点击切换、继续或新建？

只要这三个答案始终清楚，Bot 才真正具备可日常使用的多工作区、多会话体验。
